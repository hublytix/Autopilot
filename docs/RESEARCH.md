## 01. Anthropic models and structured output

Official Anthropic docs (fetched 2026-10-01 from platform.claude.com/docs, where docs.claude.com now redirects) and the official `@anthropic-ai/sdk` 0.131.0 confirm both §3 defaults, `claude-sonnet-5-5` (Active, released 2026-09-28) and `claude-haiku-4-5-20251001` (Active, retirement not sooner than 2026-10-15), and confirm that the recommended structured-output approach is GA JSON outputs via `output_config.format = { type: 'json_schema', schema }`, supported on both models with no beta header. Corrections to the brief: the two env model IDs are not interchangeable (Sonnet 5.5 returns 400 for `thinking:{type:'disabled'}`, non-default `temperature`/`top_p`/`top_k`, assistant prefill and forced `tool_choice`; Haiku 4.5 rejects adaptive thinking and does not support effort), and the fast model must be swappable through env alone because Haiku 4.5's retirement floor is close. §5.3's "faqs (8 or fewer)" and §5.4's word limits cannot be enforced by the schema grammar (`maxItems`, `maxLength`, `minLength` are unsupported), and §5.4's failure path must also handle `stop_reason` `refusal` (HTTP 200, never retried on the same model) and `max_tokens` (always a failed attempt). The SDK's documented `zodOutputFormat()` + `messages.parse()` path is rejected because in 0.131.0 it moves `enum` into description text (so category and tone values are not grammar-constrained) and `parse()` throws on invalid or truncated JSON, losing `usage`, `stop_reason` and `_request_id`; the design uses `messages.create()` with an enum-preserving project schema helper and validates with Zod v4 itself. Still open: the standard 30-day API retention figure for the privacy page rests only on a search summary of privacy.claude.com (blocked here), and nothing was run against the live API, so the hand-built schemas and the draft setting (`between_tools` at effort `medium`, a deliberate deviation from the docs; the brief uses adaptive thinking at `high`) must be checked during WIRE_UP.

## 02. HubSpot app platform, OAuth, scopes, tokens, account details, uninstall, versioning, rate limits

Sources are HubSpot's public OpenAPI spec collection, the `hubspot-project-components` templates, HubSpot CLI 8.15.0 and the Node SDKs; developers.hubspot.com pages could not be fetched from the sandbox and are cited through labelled search summaries or a verbatim third-party scrape. The brief is **corrected** in six places: (1) legacy public apps can no longer be created, so the app must be a CLI-built developer-platform project (`platformVersion` `2026.09`, `distribution` `marketplace`, `auth.type` `oauth`); (2) `requiredScopes` must be `oauth crm.objects.contacts.read forms sales-email-read`, because every email-engagement read in §5.6–5.9 needs `sales-email-read`; (3) the token-metadata `hub_domain` is the customer's website domain, so store `uiDomain`, `timeZone`, `utcOffsetMilliseconds` and `dataHostingLocation` from `GET /account-info/2026-09/details` (scope `oauth`); (4) HubSpot never pushes an uninstall webhook, which shows up only in the pull-based Webhooks Journal (`APP_LIFECYCLE_EVENT` `4-1916193`) or as a refresh failing with HTTP 400 `invalid_grant` / `BAD_REFRESH_TOKEN` (or `BAD_HUB` / `access_denied`); (5) every call uses a date-versioned path (`/oauth/2026-09/token`, `/crm/objects/2026-09/...`), since OAuth v1 endpoints stop working on 2027-02-16, v4 APIs become unsupported on 2027-03-30 and v1–v3 APIs in September 2027; (6) the official `@hubspot/api-client` still calls legacy paths, so `HubSpotClient` uses plain `fetch` with Zod. ## 03. HubSpot webhooks: v3 signature, payload, delivery, subscriptions

HubSpot signs each delivery with `X-HubSpot-Signature-v3` = `Base64(HMAC-SHA256(clientSecret, method + requestUri + rawBody + timestamp))`, where `X-HubSpot-Request-Timestamp` is a millisecond epoch string and requests older than 5 minutes are rejected; this resolves the §5.2 [VERIFY] and was confirmed byte for byte against all four official SDKs and two vendor-published vectors (developers.hubspot.com was blocked, so docs text comes from search summaries and a verbatim January 2025 community mirror). It also resolves the §5.1 [VERIFY]: HubSpot does **not** push an uninstall webhook (uninstall exists only as a pull-based Webhooks Journal event), so refresh-token failure stays the detection path, and "Disconnect" should call `DELETE /appinstalls/2026-09/external-install`, which marketplace certification has required since May 2026 (per a search summary of the changelog). Corrections to the brief: `eventId` "is not guaranteed to be unique" and duplicates and out-of-order deliveries happen (§5.2/§6), so `webhook_events` needs a composite key and `leads` its own business-level unique key; the §5.2 poller rationale ("conversion-date properties are calculated, so they can't be webhook-subscribed") is not officially documented, since the official exclusion list names only `num_unique_conversion_events` and `hs_lastmodifieddate`, though the poller stays for other reasons. §10 WIRE_UP step 1 is not "click-by-click": webhooks are configured in `src/app/webhooks/webhooks-hsmeta.json`, deployed with `hs project upload`, and settings changes can take up to 5 minutes to apply. Extensions: subscribe with `object.creation` + `objectType: "contact"` and accept both payload shapes, sign against a configured `HUBSPOT_WEBHOOK_TARGET_URL` and the raw body, write our own verifier (the official Node `Signature.isValid` defaults to v1, throws, compares in non-constant time and skips the age check for a non-numeric timestamp), return 200 for deliberately ignored events (a JSON array of up to 100 events, 5-second timeout, any 4xx/5xx retried up to 10 times over 24 hours), add a `contact.privacyDeletion` subscription that purges immediately, and keep the poller because no form-submission webhook exists.

## 04. HubSpot lead intake: form identification, submissions API, forms list, CRM search

Confirmed as the brief assumes: the forms list is `GET /marketing/v3/forms` (scope `forms`), contact reads and CRM search on `recent_conversion_date` work with `crm.objects.contacts.read`, and all of these are available on HubSpot's Free tiers. The brief is corrected in two places here: (1) contact properties cannot reliably identify the submitting form, because `recent_conversion_event_name` is a human-readable "Page title: Form name" string with no form GUID, so the primary intake source must be the legacy, spec-less `GET /form-integrations/v1/submissions/forms/{formGuid}` (scope `forms`), and the `contact.creation` webhook and contacts search become triggers only; (2) the "conversion-date properties are calculated, so they can't be webhook-subscribed" rationale is not official, since the official exclusion names only `num_unique_conversion_events` and `hs_lastmodifieddate`, and the real reason to poll is that HubSpot has no form-submission webhook event. It is corrected in two more: (3) submissions carry no contact ID, so dedupe on `(portalId, formGuid, conversionId)`, or on `(portalId, formGuid, submittedAt, lower(email))` when there is no `conversionId`, and resolve the contact by email; (4) the §5.8 baseline needs email-engagement search, which no contact property replaces, and one spec rollout requires `sales-email-read` for that search, which is outside the brief's scope set. The sources also extend the brief with the contacts-search format and limits (GTE with an overlap window, one ascending sort, epoch-ms strings, 200 per page, a 10,000-result cap, 5 requests/s), the forms-list `formTypes` parameter (send `hubspot` and `flow`), a deterministic newsletter-form heuristic, a message-extraction order that prefers submission values over the overwritten `message` property, and HubSpot's 2026 date-based path versioning (contacts and emails have dated paths; forms and form submissions do not). The sandbox blocked HubSpot's docs hosts, so docs-page claims are cited through search summaries or a verbatim third-party scrape (teostereciu/mcpsynth, 2026-04-13), with every citation labelled by kind.

## 06. Compose links: Gmail, Outlook, mailto

Only `mailto:` has an official specification (RFC 6068, with Apple and Android docs confirming it opens the default composer); Google and Microsoft document no web compose URL, so the Gmail and Outlook formats rest on de-facto usage, Chromium/Firefox source, an unofficial 2021 OWA client mirror and community tests, and every vendor behaviour must be hand-tested on real accounts before launch. The sources correct brief §5.5 in five places: (1) Outlook defaults to `{base}?mailtouri={encodeURIComponent(mailto URI)}` (the URL browsers build for the OWA `mailto:` handler) instead of plain `to=&cc=&bcc=&subject=&body=`, because plain `cc=`/`bcc=` are reported dropped (evidence conflicts) and `%2B` in a plain `to=` has been reported to become a space, with plain parameters kept as a config fallback; (2) the work host is `https://outlook.cloud.microsoft/mail/deeplink/compose`, not `outlook.office.com`, and personal is `https://outlook.live.com/mail/deeplink/compose`; (3) phone User-Agents get the `mailto:` target because Gmail and Outlook web compose links land in the inbox on phones; (4) Next.js 14's `NextResponse.redirect` defaults to 307, so 302 must be passed explicitly; (5) a bare 302 to `mailto:` is replaced by a small 200 interstitial linking to the `mailto:` URI. They extend it with the Gmail format `https://mail.google.com/mail/?view=cm&fs=1&to=&cc=&bcc=&su=&body=` (subject is `su`; Gmail rewrites it to `/mail/u/0/?…&tf=cm`; both undocumented), optional `/mail/u/{email}/` account selection, one encoder (`encodeURIComponent`, also escape `!'()*`, `toWellFormed()` first, never `URLSearchParams`; CRLF in `mailto:`, LF for Gmail) and the ~1,800-character threshold applied per client to the final URL (Outlook `mailtouri` is ~30% longer and hits it at ~154 English words, non-Latin text much sooner). BCC is guaranteed nowhere (RFC 6068 guarantees only `subject` and `body`, Outlook `bcc` is unverified in both forms, Gmail `bcc` is community-verified only), so the BCC logging address is shown on the interstitial and copy-reply pages; lead addresses are validated as one bare addr-spec, compose URLs are never logged, and sovereign-cloud owners (GCC High, 21Vianet) go to `mailto:`. Official sources settle encoding (WHATWG URL/HTML, RFC 6068, Chromium's escape table), Microsoft 365 hosts, browser URL ceilings and the Next.js default; the sandbox blocked support.google.com, developers.google.com, learn.microsoft.com, rfc-editor.org, stackoverflow.com and live probing of Gmail/Outlook, so Microsoft pages were read from MicrosoftDocs GitHub sources, RFCs from byte-identical mirrors and Microsoft Q&A only through search summaries.

## 07. Upstash QStash and Vercel Cron

The QStash answers come from Upstash's docs source repo (upstash/docs @09b815ea), the QStash and Developer API OpenAPI specs, and the `@upstash/qstash` 2.12.0 SDK source plus local SDK experiments. vercel.com and the Upstash pricing page were blocked, so the Vercel Cron facts come from Vercel's CLI source, the `@vercel/config` types, Vercel's examples repo and Vercel's official agent plugin. The §5.6 [VERIFY] is resolved: each delivery carries an HS256 JWT in `Upstash-Signature`, keyed with the signing-key string itself, with `iss` `"Upstash"`, `sub` = destination URL, `body` = base64url SHA-256 of the raw body, a 5-minute `exp` and `nbf` `0` (since September 2024), and verifiers must accept the current or the next key. The brief is corrected in seven places: (§3) Vercel Hobby likely allows only daily crons (training knowledge only), so the 5-minute poller and hourly Monday check need Vercel Pro or QStash schedules, with periodic routes accepting both triggers; (§5.9) "Monday 08:00 local" must be a catch-up due-check (local time ≥ Monday 08:00 and no `weekly_reports` row for this ISO week), because equality misses +05:30/+05:45 portals and a missed run skips the week; (§5.6) the quiet-hours/weekend shift can push the +5-day job to +7d10h, beyond the Free plan's 7-day maximum delay, so publish in hops or require pay-as-you-go; (§5.6) `lead:{id}:fu:{n}` dedupe IDs are valid but QStash deduplicates for only 10 minutes, so long-term idempotency lives in Postgres; (§7) QStash sends no timestamp header and `nbf` is `0`, so JWT `exp` (5 min plus clock tolerance) is the only time bound; (§10 step 4) there is no console callback URL, as the destination is passed with each publish from a new `APP_URL` and the region-specific `QSTASH_URL` must match the token and keys; (§10 step 3) there is no dashboard cron step, as crons deploy from `vercel.json`, run only on production deployments, are invoked with GET and need a `CRON_SECRET` env var. Not officially documented here, so re-check at WIRE_UP: Vercel Hobby cron frequency, and the QStash daily quota, maximum retries, HTTP timeout and DLQ retention.

## 08. Razorpay Subscriptions and webhooks

Razorpay signs every webhook with `X-Razorpay-Signature`, a lowercase-hex HMAC-SHA256 of the raw request body keyed with the per-webhook secret (not the API key secret), which confirms the §5.10 [VERIFY]; four test vectors (one published by Razorpay) reproduce with the official `razorpay@2.9.8` helper, `node:crypto` and `openssl`, and every docs page was read from Razorpay's official `github.com/razorpay/markdown-docs` export (commit `ab3bda5`, auto-synced 2026-04-09) because razorpay.com was blocked in the sandbox. Subscriptions have nine documented statuses and ten `subscription.*` webhook events, delivery is at-least-once and unordered, and some transitions (`created` → `expired`, a failed authentication payment) fire no webhook, so status must also be reconciled with `GET /v1/subscriptions/{id}`; the §3 "hosted checkout" is the Subscription Link (`short_url`) returned by `POST /v1/subscriptions`, and the 14-day no-card trial maps onto a future `start_at`. Corrections to the brief: (1) §7 "timestamps checked": Razorpay sends no signed timestamp header (only the body field `created_at`), retries arrive for up to 24 hours and replays cover events up to 15 days old, so a 5-minute window would reject legitimate deliveries and replay protection must come from event-id plus body-hash dedupe, monotonic per-subscription application and a `created_at` sanity window; (2) §5.10 checkout guard: "never block on `created`" is right, but blocking only on `active` and `halted` is incomplete, because `authenticated`, `pending` and `paused` are live too (a second checkout creates a second mandate), and on `created` the stored `short_url` should be reused. (3) §10 WIRE_UP step 7 "fails silently": the same-generation key requirement is right, but Razorpay's docs do not support "silently", since with server-side Subscription Links a mismatched pair fails loudly at create time ("The api key provided is invalid"); (4) §5.13 legal pages (a gap): USD pricing needs International Cards activation, which requires Terms and Conditions, Privacy, Refund and Cancellation, and Shipping policy pages, while the brief plans only `/privacy` and `/terms`, and Razorpay may reject "TODO: legal review" placeholders.

## 09. Next.js version, instrumentation, security headers, Sentry

Next.js 14 is end-of-life: 14.2.35 (2025-12-11) is the last 14.x release and has 23 open advisories (2 critical, 8 high) fixed only in 15.x/16.x, so the brief's Next 14 pin is replaced by Next.js 16.3.8 pinned exactly on Node 24 LTS (Node 22.12+ only if Vercel cannot run 24; no 15.5.27 fallback, since a community tracker puts 15.x EOL at 2026-10-21). The brief's `src/instrumentation.ts` rule holds only for a `src/app` layout: Next looks for the file only in the parent of the `app`/`pages` directory (a stray root `app/` or `pages/` moves it back to the repo root), and on Next 14 `register()` also silently never runs without `experimental.instrumentationHook: true`. `beforeSend` scrubbing alone is wrong for `@sentry/nextjs` v11 (released 2026-09-23): `sendDefaultPii` was removed, an unset `dataCollection` collects request bodies (attached verbatim), headers, cookies and query strings, `beforeSend` misses breadcrumbs, spans, logs and the envelope-header trace context, `beforeSendTransaction` is a no-op by default, and with tracing on Anthropic prompts and completions are recorded, so every `Sentry.init` must pass an explicit restrictive `dataCollection`, run errors-only (no tracing), filter out the `Anthropic_AI` and `Console` integrations, and scrub in both `beforeSend` and `beforeBreadcrumb`. Action-link tokens in the path (`/a/{token}/send|edit|dismiss`) always reach Sentry in `event.request.url` and the transaction name `GET /a/<token>/send`, which is safe only while tracing is off and `beforeSend` rewrites both; use a recognisable `apt_` prefix, carry tokens in the query string or POST body, and set `Referrer-Policy: no-referrer` on action pages. nextjs.org, docs.sentry.io and vercel.com were blocked in the sandbox, so the formal Next.js support-policy wording, Vercel's Node 24 support and the live Sentry settings labels must be re-checked at WIRE_UP.

## 10. Supabase, PGlite, Resend and React Email

Official sources support the brief's stack for this area (Supabase Postgres with SQL migrations, RLS on every table, Supabase Auth magic links, Resend with React Email, PGlite for database tests without Docker or credentials), and a local Next.js 14.2.35 build on Node 22 ran the whole stack together (V-3); because supabase.com, pglite.dev and resend.com were blocked, the evidence comes from vendor docs-source and SDK repos, npm and local experiments. The sources correct the brief in four places: (1) §3's "service-role key" is legacy naming, since Supabase is deprecating the JWT `anon`/`service_role` keys "by the end of 2026", so use the secret key `sb_secret_...` (`SUPABASE_SECRET_KEY`, server only) and the publishable key `sb_publishable_...` (`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`); (2) §3/§6 "RLS enabled on every table" is required but not enough, because projects created after 2026-05-30 do not auto-grant new `public` tables to `anon`, `authenticated` or `service_role`, so every migration must GRANT to `service_role` or the server gets `42501 permission denied`, and the secret key bypasses RLS only when no user access token is attached. (3) Supabase's built-in SMTP sends only to the project's organization team at 2 emails per hour, so no real owner can log in until custom SMTP through Resend is configured (or the app sends the link itself, V-1), which makes WIRE_UP step 2's Supabase SMTP setup depend on step 5's Resend domain verification. (4) Email scanners (for example Microsoft Defender Safe Links) prefetch links, so a GET to `/a/{token}/dismiss` must show a confirm button and dismiss only on POST, and a GET to `/a/{token}/send` is not a reliable "send clicked" signal. Still open: the Resend facts come from Resend's GitHub repos, the grants timeline from a WebFetch rendering of Supabase's announcement, and several Auth behaviours from the Auth server source on `master`, so all must be re-checked live during WIRE_UP.

## Appendix A. Method, sources and limits

**Process.**
1. Ten research agents each took one topic area. They verified the brief's claims against official sources and recorded exact strings, sources and evidence quotes.
2. An adversarial verifier then re-opened every cited source for every area. Each verifier re-ran the local experiments (signature vectors, SDK behaviour) and tried to refute every finding.
3. In total, 179 findings were reviewed: 141 upheld, 32 corrected, 6 judged insufficiently evidenced. The verifiers added 26 more items.
4. This file and `docs/research/*` show the **final** answers, with every verifier correction applied.

**Sandbox network limits.** The research ran in a sandbox whose egress proxy blocked these sites:
- developers.hubspot.com, knowledge.hubspot.com, community.hubspot.com
- razorpay.com, upstash.com, vercel.com, supabase.com, resend.com
- docs.sentry.io, nextjs.org, learn.microsoft.com, support.google.com, rfc-editor.org

platform.claude.com, GitHub (raw files and clones), the npm registry and a web search tool were reachable. For blocked sites we used, in order of preference:
- **official documentation source repositories**, which render to the public docs URLs we cite (Upstash docs, Supabase docs, Next.js docs, Sentry docs, MicrosoftDocs, Razorpay's markdown docs export);
- **official OpenAPI specs** (HubSpot-public-api-spec-collection);
- **official SDK and CLI source** (HubSpot Node/PHP/Python/Ruby SDKs, `@hubspot/cli`, `hubspot-project-components`, qstash-js, razorpay-node, the Anthropic TypeScript SDK, Sentry JavaScript, `supabase/auth`);
- **official pages via search summaries.** These are marked as such and usually rated PARTIAL in §0.

Community sources appear only as corroboration and are labelled **non-authoritative**.
